# Трекер инфляции

![Python](https://img.shields.io/badge/python-3.9%2B-blue)
![Tests](https://github.com/StigTax/inflation_tracker/actions/workflows/tests.yml/badge.svg)

Небольшое приложение для учёта покупок и анализа динамики цен.
В проекте есть **CLI** для CRUD-операций и **GUI** на **PyQt6**.

---

## Возможности

- Справочники: **магазины**, **категории**, **единицы измерения**, **продукты**
- Учёт покупок: дата, количество, сумма, комментарии, промо (если включено)
- **Пакетный ввод покупок**: одна дата и магазин на весь чек, несколько строк
  товаров разом, с быстрым добавлением нового продукта прямо из формы
- Постраничный просмотр списка покупок в GUI (без загрузки всей таблицы в память)
- При первом запуске БД автоматически наполняется стартовым набором
  категорий, единиц измерения и магазинов (см. `app/data/seed/*.csv`)
- Аналитика и графики: динамика цен/инфляции по продукту, категории,
  магазину или собственной корзине товаров — индекс Ласпейреса, Пааше
  или Фишер на выбор
- «Повторить последний чек…» — пакетный ввод, предзаполненный тем же
  набором товаров, что и в прошлый раз
- CLI-режим подходит для автоматизации и скриптов

## Технологический стек

| Слой | Технологии |
|---|---|
| БД / ORM | SQLite, SQLAlchemy 2.0, Alembic (миграции) |
| Бизнес-логика | Python 3.9+, pandas (аналитика, индексы цен) |
| CLI | argparse, prettytable |
| GUI | PyQt6, matplotlib |
| Тесты / CI | pytest, pytest-cov, pytest-qt (GUI, offscreen), ruff, GitHub Actions |
| Упаковка | PyInstaller (Windows .exe) |

<summary><b>Для технического ревью: архитектура и инженерные решения</b></summary>

### Слои приложения

```
app/
├── models/     # SQLAlchemy ORM-модели
├── crud/       # низкоуровневые операции с БД (select/insert/update/delete)
├── service/    # бизнес-правила, валидация, промо-логика, аналитика
├── cli/        # argparse-обвязка над сервисным слоем
└── gui/        # PyQt6-интерфейс над тем же сервисным слоем
```

CLI и GUI — два независимых клиента одного и того же сервисного слоя;
ни один из них не обращается к CRUD или к БД напрямую.

### Что может быть интересно при код-ревью

- **Аналитика** (`service/analytics.py::_compute_price_index`) считает индекс
  Ласпейреса, Пааше и Фишера одним общим join'ом (period × product) с базовым
  периодом — три формулы отличаются только тем, чьими количествами
  взвешивать цены, поэтому каждая точка результата содержит сразу все три
  значения (для "сверки методик"), а не только выбранный метод.
- **Промо-логика покупки** (`models/purchase.py::resolve_promo`) — правила
  согласования `is_promo`/`promo_type`/`regular_unit_price` вынесены в один
  метод вместо дублирования между созданием и обновлением записи.
- **Guard'ы на удаление** (`service/delete_guards.py`) — прикладные проверки
  перед удалением справочников (нельзя удалить категорию/магазин/единицу,
  если на неё есть ссылки), не полагаемся только на ограничения БД.
- **Логирование вызовов** (`logging/decorators.py`) — декоратор `@logged`
  с безопасной сериализацией аргументов и результата (без падений на
  тяжёлых ORM-объектах) и таймингом на старт/успех/ошибку.
- **Кэш справочников в GUI** (`gui/ref_cache.py`) — простой in-memory кэш
  с явной инвалидацией после изменений, без TTL и скрытой магии.
- **Пакетное создание покупок** (`service/purchases.py::create_purchases_batch`) —
  атомарно: либо сохраняются все строки чека, либо ни одной (без ручного
  `BEGIN`/`ROLLBACK`, за счёт отката несохранённой сессии при исключении).
- **Пагинация покупок** (`list_purchases_filtered(offset, limit)`) — GUI
  запрашивает данные постранично, аналитика по-прежнему получает выборку
  целиком (вызов без `offset`/`limit`).
- **Сид стартовых данных** (`alembic/versions/a4ff3de9f63b_...py`) —
  категории/единицы/магазины грузятся из `app/data/seed/*.csv` одноразовой
  data-миграцией, а не проверкой "пустая ли таблица" при старте: Alembic
  и так трекает применённые ревизии, так что сид гарантированно накатится
  ровно один раз за жизнь БД и не перезатрёт то, что пользователь потом
  удалит/поменяет вручную. Чтение CSV (`app/core/seed_csv.py`) намеренно
  не зависит от ORM-моделей — миграции обязаны переживать модели.
- **Тесты и CI**: pytest + pytest-cov на сервисный слой и CLI, плюс
  GUI-тесты на `pytest-qt` (запускаются в CI headless, `QT_QPA_PLATFORM=offscreen`);
  `ruff` — в GitHub Actions на каждый PR; миграции Alembic упаковываются
  прямо в exe-сборку через PyInstaller.

</details>

## Быстрый старт для пользователей (Windows)

1. Открой вкладку **Releases** в репозитории и скачай архив сборки (zip).
2. Распакуй архив в любую папку.
3. Запусти `InflationTracker.exe`.

При первом запуске приложение создаст базу SQLite и автоматически применит миграции.

---

## Где лежат база и логи

По умолчанию используется SQLite, файлы создаются в каталоге состояния пользователя (чтобы работало и из исходников, и из exe).

**Windows**
- БД: `%APPDATA%\InflationTracker\inflation.db`
- Логи: `%APPDATA%\InflationTracker\logs\logs_to_YYYY-MM-DD.log`

**Linux**
- БД: `~/.local/state/InflationTracker/inflation.db`
- Логи: `~/.local/state/InflationTracker/logs/`

**macOS**
- БД: `~/Library/Application Support/InflationTracker/inflation.db`
- Логи: `~/Library/Application Support/InflationTracker/logs/`

---

## Конфигурация БД

Источник БД выбирается в следующем порядке:

1) `--db-url` (CLI) или `DB_URL` (окружение)  
2) `./inflation.db` в корне проекта (если файл существует)  
3) каталог состояния пользователя (см. выше)

Можно положить `DB_URL` в `.env` в корне проекта — он будет подхвачен автоматически.

Пример:
```bash
export DB_URL="sqlite+pysqlite:///$(pwd)/inflation.db"
```

## Запуск из исходников (для разработки)

### Требования

Python 3.9+

### Установка

Рекомендуемый способ:

```bash
python -m venv .venv

# Windows (bash, например Git Bash):
source .venv/Scripts/activate

# Linux/macOS:
source .venv/bin/activate

pip install -e ".[testing,dev,gui]"
```

### Запуск

CLI:

```bash
python -m app.cli.main --help
```

GUI:

```bash
python -m app.gui.main
```

### Примеры CLI

Базовый сценарий: создать справочники, затем покупки.

```bash
# Категории
python -m app.cli.main category add "Еда" --description "Продукты питания"
python -m app.cli.main category list --table

# Единицы измерения
python -m app.cli.main units add "кг" --measure-type "Вес"
python -m app.cli.main units list --table

# Магазины
python -m app.cli.main store add "Пятёрочка" --description "Возле дома"
python -m app.cli.main store list --table

# Продукты
python -m app.cli.main product add "Яблоки" --category-id 1 --unit-id 1
python -m app.cli.main product list --table

# Покупки
python -m app.cli.main purchase add \
  --date 2025-01-20 \
  --product-id 1 \
  --store-id 1 \
  --quantity 2 \
  --total-price 199.90 \
  --promo \
  --promo-type discount \
  --regular-unit-price 129.90

python -m app.cli.main purchase list --table

# Фильтрация покупок по продукту и датам
python -m app.cli.main purchase list \
  --product-id 1 \
  --from-date 2025-01-01 \
  --to-date 2025-01-31 \
  --table
```

### Полезные опции

`--db-url` и `--echo-sql` доступны для всех CLI-команд.

`list` поддерживает `--full` (key: value) и `--table` (таблица).

## Сборка exe (для сопровождающих)

Сборка делается через PyInstaller (Windows). В проекте используется подход, при котором миграции Alembic упаковываются в сборку и применяются автоматически при первом запуске — в том числе одноразовый сид стартовых категорий/единиц/магазинов из `app/data/seed/*.csv`.

Перед сборкой релиза проверь содержимое `app/data/seed/*.csv` — это то, что увидит пользователь при первом запуске. Изменения в этих файлах ПОСЛЕ того, как сборка с ними уже кому-то попала (и миграция применилась), задним числом на уже существующие БД не влияют — для добавления новых дефолтов нужна новая data-миграция, а не правка старого CSV.

Типовой сценарий (onedir):

```bash
pyinstaller --noconfirm --clean \
  --name InflationTracker \
  --onedir \
  --windowed \
  --add-data "alembic.ini;." \
  --add-data "alembic;alembic" \
  --add-data "app/data/seed;app/data/seed" \
  --collect-data matplotlib \
  --collect-data pandas \
  --collect-data numpy \
  --exclude-module matplotlib.tests \
  --exclude-module numba \
  --hidden-import=pandas.core._numba \
  --hidden-import=logging.config \
  run_gui.py
```

Флаг `--hidden-import=logging.config` обязателен: без него сборка стартует
из исходников, но падает `ModuleNotFoundError` в собранном `.exe` — PyInstaller
не подхватывает этот модуль автоматически. Актуальная команда всегда есть
в `build_exe.sh` и в `.github/workflows/build-windows.yml`.

### Roadmap: путь к v1.0

Текущее состояние (`v0.4.5`) уже не ранний прототип: есть сервисный
слой, Alembic, CI, GUI-тесты, пакетный ввод, промо-логика, пагинация,
аналитика с тремя методами индекса, логирование, сид стартовых данных
и сборка под Windows. До `1.0` осознанно **не наращиваем количество
фич ради номера версии** — цель другая: пользовательские данные не
теряются, обновления предсказуемы, а не ещё одна формула индекса.

Условие готовности `1.0`: пользователь может создать данные, удобно
ими управлять, построить аналитику, экспортировать результат, сделать
и восстановить бэкап, обновиться без потери данных, а при ошибке —
понять, что случилось и где искать бэкап/логи.

**v0.5.0 — Backup / Restore / Export** (следующий шаг)
- Backup / Restore БД из GUI («Данные» → создать/восстановить копию);
- автоматический бэкап БД прямо перед `alembic upgrade head` — если
  миграция сломается, у пользователя должна остаться нетронутая копия;
- экспорт покупок в CSV.

**v0.6.0 — Settings / About + UX-полировка аналитики**
- диалог с путями к БД/логам/бэкапам, версией ревизии Alembic, кнопкой
  «создать бэкап»/«открыть папку» — сейчас это всё существует, но
  живёт «за кулисами»;
- фиксация валюты как контракта (одна БД — одна валюта), настройка
  в том же диалоге;
- явный выбор базового периода в аналитике вместо неявного «первый
  период в выборке»;
- индикатор качества данных (периодов/покупок/товаров в выборке,
  подсказка при их нехватке);
- экспорт аналитики: CSV точек графика + PNG самого графика;
- понятные сообщения при ошибках БД/миграции («данные не изменены,
  бэкап здесь», а не сырой traceback).

**v0.7.0 — `Receipt` как полноценная сущность**
- вместо того что чек сейчас — это просто «магазин + дата», отдельная
  таблица `Receipt` (`store_id`, `purchase_date`, `comment`),
  `Purchase.receipt_id` — nullable, чтобы не выдумывать связи для уже
  существующих данных задним числом;
- `create_purchases_batch()` создаёт `Receipt` + N `Purchase`;
- `get_last_receipt()` становится честным запросом по `receipt.id`,
  а не эвристикой по совпадению магазина и даты.

**v0.8.0 — Release hardening**
- прогон `alembic upgrade head` в CI не только на пустой БД, но и на
  сохранённом снэпшоте БД предыдущего релиза;
- smoke-проверка собранного exe (ресурсы на месте, БД создаётся,
  приложение стартует и закрывается без ошибок).

**v0.9.0 — Release Candidate**
- feature freeze: только баги, UX-полировка, тесты, документация —
  без новых фич вообще, это сознательное решение, не забывчивость.

**v1.0.0** — стабильный релиз без изменений функциональности
относительно RC.

---

**Осознанно вне `1.0`** (не потому что не важно, а потому что не про
персональный офлайн-трекер): cloud sync, аккаунты/авторизация,
серверный backend, мобильное приложение, автопарсинг цен магазинов,
автообновление приложения, PostgreSQL для desktop-версии,
multi-user, AI-прогнозирование.

**Отдельно за скобками `1.0`, но не забыто:**
- Шринкфляция (`package_size` на `Purchase`) — требует отдельно
  продуманной модели упаковки/нормализации объёма-массы, не то, что
  стоит впихивать перед feature freeze. Ориентир — `1.1+`.
- Именованные сохранённые корзины («Мои корзины: продукты на неделю,
  завтрак, …») — развитие уже реализованного выбора корзины кликом
  (`ProductPickerWidget`), но самостоятельная фича, не блокер `1.0`.
- Dependency lock (`requirements-lock.txt` и подобное) — осознанно
  откладываем до первого реального инцидента с несовместимостью
  зависимостей, а не строим процесс под проблему, которой ещё не было.
- Тёмная тема GUI.
